# 适配记录（nezha / OS4.0.7.0.XPACNXM）

从上游 `v0.3.1` 到这台机器能开机、能解密，一共四处改动、一次版本号。每条都附上当时的实测输出。

## 1. 基底换到 OS4.0.7.0

`devices/nezha.toml` 的 `[stock]`：

```toml
version  = "OS4.0.7.0.XPACNXM"
package  = "https://bkt-sgp-miui-ota-update-alisgp.oss-ap-southeast-1.aliyuncs.com/OS4.0.7.0.XPACNXM/nezha-ota_full-OS4.0.7.0.XPACNXM-user-17.0-5d0985edfa.zip"
recovery = "43927e2cb10fc0edc6d793e2bec8f4bc4a2e0c51b0a920b65163f4e2118bc302"
```

`skyward-pack stock` 只按 payload manifest 从整包里 range 读那 100 MiB 的 `recovery` 分区并核对 SHA-256，
不需要把 6 GB 的包整个下下来：

```
taking recovery out of the package: 104857600 bytes
wrote stock/recovery.img (104857600 bytes), its SHA-256 the one the configuration names
```

## 2. 安全元件的驱动与节点

原来 `modules.load` 只有 `synaptics_tcm2`，`/dev/st54spi_gpio` 根本不存在：

```
ls: /dev/st54spi_gpio: No such file or directory
grep -c stm_st54se /proc/modules → 0
```

补上之后：

```toml
load = ["synaptics_tcm2", "stm_st54se_gpio"]

[[owners]]
user  = "system"
group = "system"
mode  = 0o660
paths = ["/dev/st54spi_gpio", "/dev/ir_spi"]
```

```
skyward: loaded /vendor_dlkm/lib/modules/stm_st54se_gpio.ko
skyward: 2 of the phone's own files handed to the accounts its init gives them
crw-rw---- 1 system system 467, 0 /dev/st54spi_gpio
```

上游 `c5e09f6`（"wait for a file the modules just loaded make before it is handed over"）正好让 owners
在节点出现之后再改属主，所以这个顺序是安全的。

缺这步时的表现是 `E OmapiTransport: secure element not found`，weaver 回 `error 1`。

## 3. weaver 以 root 启动

节点的属主修好之后仍然不行，日志里是 loader 先失败：

```
F linker: CANNOT LINK EXECUTABLE "/odm/bin/hw/android.hardware.weaver-service.thales":
          library "libvndksupport.so" not found: needed by /vendor/lib64/libhardware.so
skyward: …weaver-service.thales: pid 714 ended: exit status: 1
```

而 Skyward 传给它的库路径是对的（这条日志是后来加的）：

```
skyward: /odm/bin/hw/android.hardware.weaver-service.thales finds its libraries in
         /system/lib64:/vendor/lib64:/vendor/lib64/hw:/odm/lib64:/mnt/system/system/lib64:/mnt/system/system/lib64/bootstrap
```

`/mnt/system/system/lib64/libvndksupport.so` 确实存在，`-rw-r--r-- root root`，目录 0755。
用同一个二进制、同一个 `LD_LIBRARY_PATH`（甚至把 `ANDROID_ROOT` 指到安装的系统）以 root 手工跑，
就能起来并注册：

```
I servicemanager: Found android.hardware.weaver.IWeaver/default in recovery VINTF manifest
D weaver-impl: GetSlots Total Slots (128)
```

差别只在运行身份。抓 `/proc` 确认 Skyward 启动的实例是：

```
Uid: 2916  Gid: 2916  Groups: 1000 1026      ← vendor_thales_weaver + system/drmrpc
```

所以把它改回 recovery 自己的用户：

```rust
// crates/skyward-programs/src/secure.rs，weaver() 里
weaver.service.user = Some("root".to_string());
weaver.service.groups = Vec::new();
```

## 4. 逐个尝试用户的所有 spblob

`locksettings.db` 记录的当前保护者是 `94a1fd91a7be3906`（weaver 槽 2），而 gatekeeper 那个
`94a1fd91a7be3907` 在本系统上不可用（见 [解密方式.md](解密方式.md)）。为了不依赖“记录的那一个恰好可用”，
`open_user_files` 改成遍历：

```rust
for protector in all_protectors(user)? {
    match open_one(service, user, &protector, credential, owner) {
        Ok(note) => return Ok(note),
        Err(e) => why.push(format!("{}: {e:#}", protector.id)),
    }
}
```

`all_protectors` 把记录的那个排在最前，其余按 id 排序；打不开时错误里带每个 id 的原因：

```
none of user 0's 2 blobs opened their files (
  94a1fd91a7be3906: android.hardware.weaver.IWeaver/default is not running; the phone's weaver has to be started first;
  94a1fd91a7be3907: have the secure world check the credential: the call failed in the driver with error -2147483646)
```

## 5. 附带的兜底与日志

`crates/skyward/src/services.rs`：凡是 `/vendor`、`/odm` 上的程序，在 `LD_LIBRARY_PATH` **末尾**
补 `/mnt/system/system/lib64` 与 `.../lib64/bootstrap`，并把最终列表写进 kmsg。
这条不是本机的关键修复（本机是第 3 条解决的），但它让“库找不到”这类问题下一眼可查。

## 6. 验证

刷入后：

```
fastboot flash recovery_a skyward-v0.3.2-nezha-OS4.0.7.0.XPACNXM.img
fastboot reboot recovery
```

解密页输 6 位 PIN，`/data`、`/sdcard` 可读；`dmesg | grep skyward` 里能看到 weaver 的库路径与
`the check of /dev/block/dm-9 ended with 0` 之类的行。
