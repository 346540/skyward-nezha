# 解密方式（小米 17 Ultra / nezha）

本文记录这台机器上 `/data` 的加密结构，以及 Skyward 是怎么把它打开的。所有结论都来自实际运行
（recovery 里的 `dmesg`、`logcat`、`/proc`），不是推测。

## 1. 三层

```
metadata 层    fstab 的 metadata_encryption → keymint 经 /metadata/vold/metadata_encryption/key → dm-default-key
每用户 FBE     /data/system_de/0/spblob/<id>.spblob + keystore2 的包装密钥
               /data/misc/keystore/persistent.sqlite，别名 synthetic_password_0
文件加密密钥   /data/misc/vold/user_keys/ce/0/current，fscrypt 挂 /data/data 与 /sdcard
```

`metadata` 层不需要用户口令，Skyward 在解密页之前就已经把 `/data` 以 `dm-default-key` 打开；
卡住的一直是第二层。

## 2. 两个保护者

`/data/system_de/0/spblob/` 下有两个 blobs，属于同一个用户、同一个口令：

| 文件 | 大小 | 含义 |
|---|---|---|
| `94a1fd91a7be3906.spblob` | 见下 | 记录在 `locksettings.db` 里的当前保护者 |
| `94a1fd91a7be3907.spblob` | | 备用/旧保护者 |

各自的附属文件：

```
94a1fd91a7be3906.pwd      口令参数：kind=3（PIN），cost=[9,3,1]，salt=a222b88f831d3acbc0b60480ec589700，enrolled=0 字节
94a1fd91a7be3906.weaver   01 00000002  → weaver 槽号 = 2
94a1fd91a7be3907.pwd      同一套 salt / cost（Android 复用了同一份）
94a1fd91a7be3907.secdis   secdiscardable 变换用的字节
94a1fd91a7be3907（无 .weaver，enrolled 58 字节）
```

两者对应的 keystore2 别名都是 `synthetic_password_0`。

## 3. 两条打开路径

### 3.1 weaver（首选，本机唯一可用）

```
PIN
 → scrypt(kind=3, cost=[9,3,1], salt)                 stretched（128 字节）
 → personalizedHash("weaver-key") → AES 密钥
 → android.hardware.weaver.IWeaver/default 读槽 2     value（16 字节）
 → personalizedHash("weaver-pwd", value)              protector secret
 → keymint 用包装密钥 GCM 解 spblob                    inner（128 字节）
 → 内层再解出 synthetic_password_0
```

weaver HAL 本身要经 **OMAPI** 打开 eSE：

```
weaver 进程
 → android.se.omapi.ISecureElementService/default      （recovery 里由 Skyward 自己 serve）
 → android.hardware.secure_element.ISecureElement/eSE1  （secure_element-service.qti）
 → /dev/st54spi_gpio                                    （stm_st54se_gpio 驱动建立的 SPI 通道）
 → ST54L applet，2 号槽
```

这条链上任何一环缺失，日志里都会留下不同的行：

| 现象 | 日志 |
|---|---|
| 驱动没加载/节点不存在 | `ls: /dev/st54spi_gpio: No such file or directory`，`isCardPresent` → false |
| 节点权限不是 `system:system` | `E OmapiTransport: secure element not found` |
| weaver 起不来（loader 停在 libvndksupport） | `CANNOT LINK EXECUTABLE …: library "libvndksupport.so" not found`，`F linker` |
| weaver 没注册 | `94a1fd91a7be3906: android.hardware.weaver.IWeaver/default is not running` |
| weaver 起来了但 eSE 不通 | `94a1fd91a7be3906: ask the weaver about itself: the service refused the call with its error 1` |

修好之后 `service call android.hardware.weaver.IWeaver/default 1` 会给出
`status=0, slots=1, key=0x10, value=0x10` 这样的回包（`logcat` 里是 `GetSlots Total Slots (128)`）。

### 3.2 gatekeeper（兜底，本系统不可用）

```
PIN → scrypt → same stretched
 → android.hardware.gatekeeper.IGatekeeper/default verify(TYPED_SLOT+0=100000, enrolled, gatekeeper_password(stretched))
 → note
 → keymint 用包装密钥 + note 解 3907 的 spblob
```

在这台机器的 `OS4.0.7.0.XPACNXM` 上，gatekeeper HAL 内部就坏了：

```
qti-gatekeeper-hal: channel: KeymintVersion { status: 0, hal_version: 0, ta_version: (0, 0, 0) }
qti-gatekeeper-hal: In this response packet: [255, 255, 255, 255, 0, 0, 0, 0] with rsp.len: 4096 and header length: 4294967295
qti-gatekeeper-hal: Response size is greater than response buffer. This should never happen!!
```

它和 keymint HAL 之间的 TA 通道拿到的是 `0xFFFFFFFF` 的错误头，`verify` 只能回
`the call failed in the driver with error -2147483646`。这跟 Skyward 的 binder 实现无关
（0.1.2 时代同样的调用在 4.0.6.0 上是通的），是这一版系统上 gatekeeper 侧的问题，
从 recovery 里改不动。

所以本机只能走 weaver：Skyward 必须把用户所有 `spblob` 都试一遍（`open_user_files` 的循环），
而不能只看 `locksettings.db` 记录的那一个——记录的正是 3906（weaver），但历史上也出现过记录的
是不可用那个的情况，循环才是稳的。

## 4. 相关常量（`skyward-crypto`）

| 名 | 值 |
|---|---|
| `PROTECTOR_SECRET` | `"application-id"` |
| `WEAVER_KEY` | `"weaver-key"` |
| `WEAVER_VALUE` | `"weaver-pwd"` |
| `SECDISCARDABLE` | `"secdiscardable-transform"` |
| `TYPED_SLOT` | `100000`（gatekeeper 里用户的口令槽 = 100000 + uid） |
| `personalizedHash(x)` | `SHA512(x 补到 128 字节 ‖ parts)` |

## 5. 改锁屏密码之后

Android 会重新生成 salt 与 blobs（`locksettings.db` 里的记录也换），旧的 `CAPTURED` 之类派生物全部失效。
Skyward 每次都是现场从 PIN 推，所以只要新 PIN 和新 blobs 一致就能开；但如果新系统把保护者换成
只有 gatekeeper 能开的那种，这条路又会断——这时刷回原厂 recovery 即可，数据不会丢。
